This plan converts the roadmap's `0.1.0-alpha.1 - Foundations` gate into an executable
sequence. It does **not** re-open product scope — that is fixed by the roadmap/SRS. It fixes

## 0. Decision 1 — Repository layout

**Decision: a single monorepo, in this existing repository, with top-level `backend/` and
`frontend/`. The legacy 2012 Android tree is archived into `legacy/android/`.**

### Why monorepo (not separate repos)

| Factor | Monorepo (chosen) | Separate repos |
|---|---|---|
| API-contract changes (DRF serializer ↔ TS client) | one atomic commit | two PRs, version skew |
| Local dev | one `docker-compose up`, one `make` | clone + wire two repos |
| CI | one workflow, shared secret scan | duplicated config |
| Pilot scale (1–3 devs) | low coordination cost | overhead with no payoff |
| Cooperative ownership/audit | one place to govern, one history | split governance surface |

At pilot scale (20–50 workers, 1–3 developers) the only argument for separate repos —
independent deploy cadence and team boundaries — does not yet apply. The roadmap itself
specifies a **modular monolith** on the backend; a monorepo is the natural host for it.
Splitting is a reversible later move (`git subtree split`) if a team boundary ever appears.

### Why archive, not modernize-in-place

The roadmap and legacy audit already rule the 2012 Android/Django code **archival**. It stays
in git history (moved with `git mv`, history preserved) for product memory, but it leaves the
repo root so the modern monorepo is clean.

The separate legacy Django server (`skishchampi/django-btp`, local clone under the CommonerLLP
workspace; Django ~1.5, app `btp`) is **fully audited** — see [legacy audit §3](../aapnisociety-legacy-audit.md).
It stays in its own clone; **do not import it**. Its models (`Gossip`, `Services`,
`Data`, `User_Provides`, `User_Wishes`, `Ratings`, `EnterAndReadGossip`) and SQLite snapshot
hold **no migratable data** (all tables 0 rows, 1 auth_user). Concepts are already mapped into
the modern schema: `Services`→`ServiceCategory` (this gate); `User_Wishes`/`User_Provides`→
`ServiceNeed`/`ServiceOffer` (alpha.2); `Ratings`/`Data`→private reference metadata, never
public ratings (alpha.4); `Gossip`→moderated safety notes (alpha.5). **Migrate concepts, not
code or data.** Nothing in `django-btp` is needed for alpha.1.

## 1. Engineering decisions locked for alpha.1

These are derived from the SRS/roadmap, not new product choices:

1. **Custom `User` model with phone as `USERNAME_FIELD`.** Django makes the user model a
   one-way door at first migration, so it must land before any other app migrates. Phone is
   the identity because auth is phone-OTP (SRS §5.1). Email is optional/secondary.
2. **JWT access + rotating refresh** via `djangorestframework-simplejwt`. The SRS §6.2
   explicitly asks for "short-lived access tokens and rotating refresh tokens" — that *is*
   JWT access+refresh with blacklist-on-rotate. (Not session cookies.)
3. **Dev OTP, no SMS gateway.** OTP codes are generated, hashed, stored with expiry, and
   **logged to the console / returned only when `DEBUG=True`**. A real SMS provider is a
   beta.1 concern. This satisfies "development OTP flow."
4. **Django admin *is* the alpha.1 admin console.** "Basic admin login" + "admin can view
   users and profiles" is met by `/admin/` with `User`, `WorkerProfile`, `HouseholdProfile`,
   and geo models registered. A bespoke coop console is alpha.5/beta work.
5. **PostGIS-ready without GIS code yet.** Use the `postgis/postgis` Postgres image from day
   one (so the DB engine never has to migrate), but model location as nullable
   `lat`/`lng` decimals for now. Swap to `PointField` when geo features arrive (0.3.0).
6. **Modular monolith, three apps this gate:** `accounts`, `members`, `geo`. The other SRS
   modules (introductions, moderation, notifications, search, admin_ops) are stubs created in
   later alpha milestones, not now.
7. **`AuditEvent` model is scaffolded now** (foundational, cheap) but full coverage of
   sensitive actions is wired per-feature in later milestones.

## 2. Data model — alpha.1 only

### `accounts`
- **`User(AbstractBaseUser, PermissionsMixin)`** — `phone` (E.164, unique, `USERNAME_FIELD`),
  `email` (nullable, unique), `full_name`, `primary_role`
  (`worker|household|connector|moderator|operator|admin`), `is_active`, `is_staff`,
  `is_superuser`, `date_joined`. Custom manager (`create_user(phone)`, `create_superuser`).
- **`OTPChallenge`** — `phone`, `code_hash`, `purpose` (`login|signup`), `expires_at`,
  `consumed_at` (nullable), `attempts`, `created_at`. Codes hashed, short TTL (e.g. 5 min),
  attempt cap, rate-limited per phone (SRS §6.2).
- **`AuditEvent`** — `actor` (FK User, nullable), `action`, `target_type`, `target_id`,
  `metadata` (JSON, sensitive fields redacted), `created_at`.

### `geo`
- **`City`** — `name`, `state`, `slug`.
- **`Locality`** — `city` FK, `name`, `slug`.
- **`Building`** — `locality` FK, `name`, `address`, `lat`/`lng` (nullable decimals).
- **`Unit`** — `building` FK, `label` (e.g. `A-204`).

### `members`
- **`ServiceCategory`** — `key`, `label`, `is_active`. Seed: maid, cook, driver, plumber,
  electrician, caregiver.
- **`WorkerProfile`** (1:1 User) — `display_name`, `languages` (JSON list),
  `service_categories` (M2M `ServiceCategory`), `localities_served` (M2M `Locality`, optional),
  `availability` (JSON, minimal), `default_rate_floor` (nullable decimal — detailed
  `WorkerRate` deferred to alpha.4), `contact_visibility` (choices), timestamps.
- **`HouseholdProfile`** (1:1 User) — `display_name`, `building` FK (nullable), `unit` FK
  (nullable), minimal privacy flags, timestamps.

> Privacy guardrails enforced from the start (SRS §6.1): **no** caste / religion / marital /
> relationship fields anywhere in the schema. This is a hard schema rule, not a later filter.

## 3. API surface — alpha.1 (`/api/v1/`)

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/otp/request/` | `{phone, purpose}` → issue OTP (code logged in dev) |
| POST | `/auth/otp/verify/` | `{phone, code}` → `{access, refresh, user}` |
| POST | `/auth/token/refresh/` | rotate access (SimpleJWT) |
| POST | `/auth/logout/` | blacklist refresh token |
| GET  | `/me/` | current user + which profile exists + role |
| PUT  | `/me/worker-profile/` | create/update worker profile |
| PUT  | `/me/household-profile/` | create/update household profile |
| GET  | `/geo/cities/`, `/geo/localities/`, `/geo/buildings/` | onboarding lookups (read) |
| —    | `/admin/` | Django admin (staff) |
| —    | `/api/v1/schema/` + `/docs/` | drf-spectacular OpenAPI + Swagger |

CORS via `django-cors-headers` (dev origin only). Writes idempotent where practical (SRS §7.4).

## 4. Execution phases (each phase ≈ one reviewable commit)

### Phase 0 — Restructure & lock layout
- `git mv` the legacy Android tree (`src/`, `res/`, `bin/`, `AndroidManifest.xml`,
  `.classpath`, `.project`, `.settings/`, `project.properties`, `proguard-project.txt`,
  `ic_launcher-web.png`, `libs/`) → `legacy/android/`. History preserved.
- Replace the Android `.gitignore` with a modern monorepo `.gitignore`
  (`__pycache__/`, `.venv/`, `node_modules/`, `dist/`, `.env`, `*.sqlite3`, etc.); keep the
  `legacy/android/` ignores scoped.
- Add `Makefile` (`up down migrate seed test lint fmt hooks`) and `make hooks` installing a
  pre-commit hook that blocks secrets + stray `data/`-style artifacts. **Resolves the
  takestock warning that the pre-commit hook is missing.**

### Phase 1 — Backend scaffold
- `backend/` with `uv` + `pyproject.toml`: Django 5.x, DRF, simplejwt, django-cors-headers,
  django-environ, drf-spectacular, psycopg[binary], pytest-django, ruff.
- `config/` project, settings split (base/dev/prod), env-driven secrets, `.env.example`.
- **Custom `User` first**, then `geo`, `members`; initial migrations.
- OTP flow + auth endpoints + `/me/` + profile endpoints + geo read endpoints.
- Register all models in Django admin.
- `manage.py seed_dev`: service categories + Ahmedabad/Prahladnagar/sample building + one demo
  worker and one demo household user.
- Tests: OTP request→verify→token, `/me/` role resolution, profile create, model smoke.

### Phase 2 — Frontend scaffold
- `npm create vite@latest frontend -- --template react-ts`; add `vite-plugin-pwa`,
  `@tanstack/react-query`, `react-router-dom`, a typed fetch client, `vitest`.
- Screens: **SignIn** (phone → request OTP → enter code → verify), **Onboarding** (choose
  worker/household, create minimal profile), **Dashboard** (renders `/me/`: name + role +
  sign-out). Token storage with refresh handling.
- PWA manifest + service worker (installable shell — a roadmap "should ship", cheap to do now).
- One vitest smoke test (renders SignIn, mocks OTP request).

### Phase 3 — Compose + CI + acceptance
- `infra/docker-compose.yml`: `db` (`postgis/postgis:16`), `redis` (declared for later),
  `backend`, `frontend`; `.env.example`; Dockerfiles.
- `.github/workflows/ci.yml`: backend (ruff + pytest against a Postgres service), frontend
  (eslint + vitest + `vite build`), secret scan (gitleaks). `make test` runs both locally.
- Run the acceptance walkthrough (§5) end-to-end on a clean `make up`.

### Phase 4 — Docs & closeout
- Write `docs/releases/0.1.0-alpha.1.md` once acceptance passes.
- Flip the roadmap §5 milestone status to *Met*; run `/pm` to recompute `docs/STATUS.md`.
- `/maintain` to update HANDOFF/TODO and close the WORKING.md row.

## 6. Explicitly NOT in this gate

Per roadmap §4 "Out of Scope" and the milestone boundary: no introductions, references, rate
bargaining logic, safety notes, moderation queues, payments, marketplace, public search,
native apps, SMS gateway, or algorithmic matching. Those begin at alpha.2+.

## 7. Open implementation choices (low-stakes; defaults chosen, flag to override)

1. **Backend package manager:** default `uv` (fast, lockfile). Override → pip-tools/Poetry.
2. **Frontend token storage in dev:** default in-memory access token + refresh on 401
   (localStorage fallback for dev reload). Httponly-cookie hardening is a beta.1 security task.
3. **Whether to move legacy now or after backend lands:** default move first (Phase 0) so the
   root is clean before scaffolding. Low risk — pure `git mv`, fully reversible.

None of these block starting; they are noted so a reviewer can redirect before code lands.
